* Stage 5: Skills Integration

Goal: Distribute Claude Code skills alongside AI collaboration templates.

Skills are self-contained, filesystem-based packages of task-specific
instructions (each a folder with a =SKILL.md=) that Claude loads on-demand
when the current task calls for them. The skill's description sits in
context by default; the full file is read only when relevant.

Two variants:
- *Anthropic pre-built skills* (e.g. =xlsx=, =docx=, =pptx=, =pdf=) — no
  distribution needed; reference by name.
- *Custom skills* — user/org-defined; these are what we distribute through
  the templates tree.

The natural fit with aiActivity's existing =mother/= + activity-specific
override pattern:
- =mother/_skills/= — skills available to every activity (baseline).
- =<activity>/_skills/= — activity-specific skills (e.g. a =bisos-pip-release=
  skill under =bisos-pip/_skills/= for version bumps and PyPI publishing).

=initiate= would symlink =.claude/skills/= the same way it currently
symlinks =.claude/settings.json= and =.claude/commands=. =deClaudify=,
=aiSuspend=, and =aiResume= all need to handle the new =.claude/skills=
symlink the same way they handle the other =.claude/= entries.

* Stage 6: Subproject Overlays via initiateSub

Goal: A separate command that installs only the subproject-specific state
(=CLAUDE.md=, =AI-Activity.org=, =AI-DevStatus.org=, =AI-WorkPlan.org=) in
a subdirectory, requiring an already-=initiate=-d ancestor. The invariants
(=AI-WORKFLOW.org=, =.claude/=) are inherited from the
ancestor via Claude Code's walk-up.

Motivation: nested projects should not re-install the invariants at every
level. Doing so wastes context (Claude reads the same twice)
and creates ambiguity about which activity applies. A slim overlay keeps
subproject state local without duplicating the base.

** DONE [#A] <<16.4>> Add /bx-context-trim --- in-session counterpart of startupClaudeTokens
CLOSED: [2026-10-07 Wed] SCHEDULED: <2026-10-07 Wed>

Originally floated as =/bx-aiStatus-tokens=. Named =/bx-context-trim= per the
object-then-verb convention (see [[14.11]]).
----- Results: ------

What it does and does not do:
- It does *not* report the current session's context. Claude Code's built-in
  =/context= already does that, measured. A model cannot inspect its own
  context, so anything it reported would be a worse estimate.
- The gap it fills is the *next* session plus judgment. It runs
  =aiActivity.cs -i startupClaudeTokens=, then Claude ranks trim candidates:
  - heavy =@= imports: drop the =@= or move into a skill
  - DONE subtrees: =/bx-archive=
  - stale DevStatus sections: =/bx-update-status=
  - =!! resolved via symlink=: =refresh=
  - truncated auto-memory
- Each candidate gets its real path, repo, and *shared/local* status. A shared
  template edit (e.g. an activity's =AI-Activity.org=) affects every project
  symlinked to it, and is confirmed separately.
- An optional argument sets a target token budget.
- It changes nothing without confirmation. Afterwards it re-runs the CLI and
  reports the actual saving.

Files:
- =mother/_claude/commands/bx-context-trim.md= (templates tree, =bisos/defaults=
  repo). Every initiated project has it via the =.claude/commands= symlink.
  No settings change was needed: =aiActivity.cs *= is already pre-authorized
  in =mother/_claude/settings.json=.
- =mother/AI-WORKFLOW.org=: new row in the slash-commands table (shared file,
  =bisos/defaults= repo).
- =README.org=: an "Inside a session" paragraph in the startupClaudeTokens
  section separating =/context= (now, measured), =startupClaudeTokens=
  (next, estimated) and =/bx-context-trim= (advice).
