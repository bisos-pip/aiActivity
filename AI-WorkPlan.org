* Stage 5: Skills Integration

Goal: Distribute Claude Code skills alongside AI collaboration templates.

Skills are self-contained, filesystem-based packages of task-specific
instructions (each a folder with a =SKILL.md=) that Claude loads on-demand
when the current task calls for them. The skill's description sits in
context by default; the full file is read only when relevant.

Two variants:
- *Anthropic pre-built skills* (e.g. =xlsx=, =docx=, =pptx=, =pdf=) — no
  distribution needed; reference by name.
- *Custom skills* — user/org-defined; these are what we distribute through
  the templates tree.

The natural fit with aiActivity's existing =mother/= + activity-specific
override pattern:
- =mother/_skills/= — skills available to every activity (baseline).
- =<activity>/_skills/= — activity-specific skills (e.g. a =bisos-pip-release=
  skill under =bisos-pip/_skills/= for version bumps and PyPI publishing).

=initiate= would symlink =.claude/skills/= the same way it currently
symlinks =.claude/settings.json= and =.claude/commands=. =deClaudify=,
=aiSuspend=, and =aiResume= all need to handle the new =.claude/skills=
symlink the same way they handle the other =.claude/= entries.

* Stage 6: Subproject Overlays via initiateSub

Goal: A separate command that installs only the subproject-specific state
(=CLAUDE.md=, =AI-Activity.org=, =AI-DevStatus.org=, =AI-WorkPlan.org=) in
a subdirectory, requiring an already-=initiate=-d ancestor. The invariants

level. Doing so wastes context (Claude reads the same twice)
and creates ambiguity about which activity applies. A slim overlay keeps
subproject state local without duplicating the base.

* Stage 18: Two Template Trees, Assembled into One Base

<<Stage 18>>

Goal (decided with Mohsen 2026-10-19/20): fully separate the two layers of a templates tree, so that
each is maintained on its own and a fork takes the workflow layer whole, by git, instead of receiving
copies. Supersedes Stage 17's copy-sync (=aiActivityCmnds.cs=) once migrated.

*The design.*
- A templates base, =./ai-templates/= (the directory the engine already uses), contains two inputs with
  *fixed names*: =aiTemplates-workFlow/= and =aiTemplates-DE/=. Each is a real directory or a symlink
  to a clone anywhere; only the names are fixed. All three have the *same structure* (=mother/=,
  =<activity>/=, =_nonTemplate_/=).
- *=aiActivityAssemble.cs=* generates the aggregate in =./ai-templates=: everything an input provides
  appears in the base at the same relative path. No =./all= tree: the base is the aggregate.
- *Deep merge*: directories are real directories in the base; files are relative links into the inputs;
  a symlink found in an input is reproduced as the same symlink in the base (so a relative link such as
  =bisos-pip/_skills -> ../mother/_skills= resolves against the base, i.e. the merged =mother/_skills/=).
  This keeps every path existing projects link to (=mother/...=, =<activity>/...=, =<activity>/_skills=)
  valid after the switch.
- *No layering*: a path provided by both inputs is an error, not an override. Base-level files that are
  not generated (a tree's own =README.org=, =LICENSE=, self-hosted =AI-*.org=, =.aiActivity.cs/=) are
  never touched; the assembler manages only the links it made (recorded in a manifest) and refuses to
  overwrite a real file.
- *Boundary*: =aiTemplates-workFlow= = BISOS-AI-Workflow: =mother/{CLAUDE.md, AI-WORKFLOW.org,
  AI-DevStatus.org, AI-WorkPlan.org, initiateSub/, _claude/}=, the workflow skills
  (=mother/_skills/{authoring-skills, bx-ai-commands-authorship}=), the generic activities (=aiActivity=,
  =custom=, =basic=), =_nonTemplate_/=. =aiTemplates-DE= = BISOS-Digital-Ecosystem-Skills:
  =mother/{AI-Activity.org, AI-Outputs.org}=, the other =mother/_skills/=, the ecosystem activities
  (=astro-site=, =bisos-core=, =bisos-pip=, =blee-panels=, =graphviz-pcs=, =lcnt=, =pycs=, =sbom+cap=,
  =xu-single=).
- *Where they live* (Mohsen, 2026-10-20): =/bxRepos/bxexamples/aiTemplates-workFlow= and
  =/bxRepos/bxexamples/aiTemplates-DE=, to become repos later. Both the BISOS base
  (=bisos/defaults/ai-templates=) and the public base (=bxexamples/aiActivityTemplates=) link their two
  inputs to these, so the two bases are permanently in sync. The fork links =aiTemplates-workFlow=
  to a clone and keeps its own content as a real =aiTemplates-DE/=.
