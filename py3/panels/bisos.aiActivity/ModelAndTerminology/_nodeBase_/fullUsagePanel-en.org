** +
The model and terminology of AI-Activities and of the sessions that work on them: two kinds of
root that had been one word, the rules that relate them, and the commands that follow.

Status: agreed in discussion between Mohsen and Claude on 2026-11-02, and implemented the same day:
layer 1 =aiActivity.cs -i activityReport= / =-i sessionRootCheck= (this repo, 23.1); layer 0
=AI-WORKFLOW.org= and the commands =/bx-session-start=, =/bx-session-report=, =/bx-activity-reach=,
=/bx-activity-report= (aiTemplates-workFlow 6.1; the old =/bx-confirm-root=, =/bx-confirm-here= are
aliases); layers 2 to 5 and the driver (bisos-pip/vscodeClaude 5.1, blee/vscode-claude 14.1:
=sessionStart=, =activityReach=, =rootOpen=). Where it came
from: starting Blee + VS Code Claude from scratch on a VM, and VS Code's model explained for Emacs
users. See:

####+BEGIN: blee:bxPanel:foldingSection :outLevel 1 :title "Two Roots, Not One" :anchor "TwoRoots" :extraInfo "where the confusion came from"
* [[elisp:(show-all)][(>]]  _[[elisp:(blee:menu-sel:outline:popupMenu)][±]]_  _[[elisp:(blee:menu-sel:navigation:popupMenu)][Ξ]]_       [[elisp:(outline-show-subtree+toggle)][| *Two Roots, Not One:* |]] <<TwoRoots>>   where the confusion came from  [[elisp:(org-shifttab)][<)]] E|
####+END
** +
"Root" had meant two different things, and they were never separated:

1. *The root of an AI-Activity* --- a directory on the file system, with its =CLAUDE.md= chain.
   It exists whether or not any Claude is running.
2. *The root of a session* --- the directory a Claude session runs in. In VS Code it is the
   session's window's folder, fixed when the window is opened, for the life of the session.

=/bx-confirm-root= confirmed "the session's root AI-Activity": the AI-Activity found at the
session's directory. That silently assumed the two coincide. They often do, but not always: a
VS Code window may be opened on a sub-directory, on =/bxRepos=, or on no folder at all; and a
session routinely works on AI-Activities other than the one it started in.

The two also decide different things:
- *The session's root decides the tooling*: which =/bx-= commands exist, the skills found at
  startup, permissions, hooks, project settings (=.claude/=).
- *The AI-Activity decides the content*: the =CLAUDE.md= chain, the AI-WorkPlan, the AI-DevStatus.
Reaching another AI-Activity brings its content, never its tooling.
** -B|
####+BEGIN: blee:bxPanel:foldingSection :outLevel 1 :title "Terminology" :anchor "Terms" :extraInfo "the terms, defined"
* [[elisp:(show-all)][(>]]  _[[elisp:(blee:menu-sel:outline:popupMenu)][±]]_  _[[elisp:(blee:menu-sel:navigation:popupMenu)][Ξ]]_       [[elisp:(outline-show-subtree+toggle)][| *Terminology:* |]] <<Terms>>   the terms, defined  [[elisp:(org-shifttab)][<)]] E|
####+END
** +
| Term                         | What it is                          | How it is recognized         |
|------------------------------+-------------------------------------+------------------------------|
| AI-Activity                  | Any directory with a =CLAUDE.md=      | =CLAUDE.md=                    |
| AI-Activity Root             | Made by =aiActivity.cs -i initiate=   | =.claude/=, =AI-WORKFLOW.org=    |
| Sub-AI-Activity              | By =initiateSub=: content, no tooling | =CLAUDE.md= only               |
| Session-Root                 | A session's working directory       | An AI-Activity Root (rule 1) |
| A session's root AI-Activity | The AI-Activity Root there          | The same directory           |
| Home (of an AI-Activity)     | The AI-Activity Root it sits under  | The first root walking up    |
| Native AI-Activity           | Its home is the Session-Root        | Under the Session-Root       |
| Foreign AI-Activity          | Its home is another root            | Outside the Session-Root     |

- *AI-Activity Root*: carries the tooling (=.claude/commands=, =.claude/skills=,
  =.claude/settings.json=) and the invariants (=AI-WORKFLOW.org=). Usually a git repository's top.
- *Sub-AI-Activity*: =CLAUDE.md=, =AI-Activity.org=, =AI-DevStatus.org=, =AI-WorkPlan.org= only;
  its tooling and invariants come from the AI-Activity Root above it. It may be /homogeneous/ (its
  activity's skills are the root's) or /heterogeneous/ (its own =.claude/skills= resolve elsewhere).
- *Session-Root*: engine-neutral on purpose (layers 0 and 1 name no engine); in VS Code Claude it is
  the window's folder.
- *Home*: every AI-Activity has exactly one, the AI-Activity Root it sits under (itself, for a
  root). A property of the file system: no session is involved.
- *Native* and *Foreign* are relative to a session: an AI-Activity is native to the session whose
  Session-Root is its home, and foreign to every other session. The session's root AI-Activity and
  its subs are native; other AI-Activity Roots and their subs are foreign.
- Native AI-Activities run under their own root's tooling (a heterogeneous sub excepted: its skills
  differ); foreign ones never get their root's tooling. Native work is committed in the session's
  own repository and checked by its =/bx-session-verify=; foreign work belongs to another root's.
- *Reach* is the verb, for both kinds: =/bx-activity-reach <dir>=. "Reached" and "here" are no
  longer categories.
** -B|
####+BEGIN: blee:bxPanel:foldingSection :outLevel 1 :title "The Rules" :anchor "Rules" :extraInfo "how the terms relate"
* [[elisp:(show-all)][(>]]  _[[elisp:(blee:menu-sel:outline:popupMenu)][±]]_  _[[elisp:(blee:menu-sel:navigation:popupMenu)][Ξ]]_       [[elisp:(outline-show-subtree+toggle)][| *The Rules:* |]] <<Rules>>   how the terms relate  [[elisp:(org-shifttab)][<)]] E|
####+END
** +
1. *A Session-Root must be an AI-Activity Root* --- not a sub-AI-Activity, not a directory without
   one (=/bxRepos=), not "no folder". Only an AI-Activity Root carries the tooling a session needs.
2. *A session has exactly one Session-Root*, for its whole life; its root AI-Activity is the
   AI-Activity Root there.
3. *One VS Code window is one Session-Root* (one folder per window, no multi-root workspaces).
   Several sessions in one window share it.
4. *A session may reach any AI-Activity*, native or foreign. Reaching brings content (read through
   the Read tool), not tooling.
5. *A conflict is two sessions working on the same AI-Activity at once* --- two Claudes editing one
   AI-WorkPlan. It arises in two ways:
   - a foreign reach into an AI-Activity that is native to another running session (the common
     case: being native does not protect an AI-Activity from another session reaching in);
   - two sessions at the same Session-Root (several sessions in one window, or a terminal Claude
     started there), which share all their native AI-Activities.
   Both are accepted, because reaching across roots is common and useful. The reports say when it is
   the case, naming the other session, so the user knows.
6. *The rules are checked in both places*: by the commands themselves (layer 0, so they hold
   without Blee), and by Blee before it opens a window or starts a session (layer 5).
** -B|
####+BEGIN: blee:bxPanel:foldingSection :outLevel 1 :title "Commands" :anchor "Commands" :extraInfo "the /bx- commands of a session"
* [[elisp:(show-all)][(>]]  _[[elisp:(blee:menu-sel:outline:popupMenu)][±]]_  _[[elisp:(blee:menu-sel:navigation:popupMenu)][Ξ]]_       [[elisp:(outline-show-subtree+toggle)][| *Commands:* |]] <<Commands>>   the /bx- commands of a session  [[elisp:(org-shifttab)][<)]] E|
####+END
** +
A slash command cannot create a session: VS Code (or a terminal) does. So starting has two halves:
the editor creates the session at a Session-Root; the session's first prompt orients it.

| Command                   | When                | What it does                           |
|---------------------------+---------------------+----------------------------------------|
| =/bx-session-start=         | First prompt        | Check rule 1, read the chain, register |
| =/bx-session-report=        | Any time, read-only | Where this session stands              |
| =/bx-session-verify=        | Before closing      | Records and commits complete           |
| =/bx-activity-reach <dir>=  | To work on another  | Read its chain, native or foreign      |
| =/bx-activity-report <dir>= | Any time, read-only | Where it stands relative to us         |

- */bx-session-start*: refuses when the Session-Root is not an AI-Activity Root, naming the nearest
  AI-Activity Root above it. Otherwise reads the import chain (what =/bx-confirm-root= does today)
  and reports. With =emacs=<socket>= and =register=<function>= it registers the session with Blee.
  Replaces =/bx-confirm-root=.
- */bx-session-report*: the Session-Root, its root AI-Activity and activity type, the native and
  the foreign AI-Activities reached so far, the partner Emacs if registered. Reads nothing new.
- */bx-activity-reach <dir>*: today's =/bx-confirm-here=, under the new name: resolve =<dir>= to its
  AI-Activity, read its chain (and, if heterogeneous, its skills' frontmatter), make it the active
  context. Replaces =/bx-confirm-here=.
- */bx-activity-report <dir>*: for =<dir>= (default: the current context), without reading its chain:
  - native or foreign to this session, and its home;
  - is it an AI-Activity Root or a sub;
  - homogeneous or heterogeneous (its skills against its root's);
  - its activity type (=AI-Activity.org='s target);
  - is it this session's root AI-Activity, already reached, or not yet;
  - a conflict (rule 5), where that can be known: "foreign; native to a running session at
    <root>", or "native; another session runs at this Session-Root".
- Old names kept as aliases for a while, then removed: =bx-confirm-root=, =bx-confirm0=
  (to =bx-session-start=), =bx-confirm-here= (to =bx-activity-reach=).
** -B|
####+BEGIN: blee:bxPanel:foldingSection :outLevel 1 :title "In Blee" :anchor "Blee" :extraInfo "blee/vscode-claude, layers 3 to 5"
* [[elisp:(show-all)][(>]]  _[[elisp:(blee:menu-sel:outline:popupMenu)][±]]_  _[[elisp:(blee:menu-sel:navigation:popupMenu)][Ξ]]_       [[elisp:(outline-show-subtree+toggle)][| *In Blee:* |]] <<Blee>>   blee/vscode-claude, layers 3 to 5  [[elisp:(org-shifttab)][<)]] E|
####+END
** +
- *Layer 3*, =b:vscode/rootOpen <dir>= (its WorkPlan 10.3, reopened): open =<dir>= as a VS Code
  window's folder --- bring forward the window that already has it, else a new window. Never replace
  another window's folder (that reloads it and ends its sessions).
- *Layer 4*: a session carries its Session-Root; a generic start opens a window at a directory and
  starts a new session there (the fix for "new" doing nothing). The session chosen for a buffer: its
  association first, then a session whose Session-Root covers the buffer.
- *Layer 5*:
  - =sessionStart= (replaces =confirmRoot=): from the buffer, walk up to the nearest AI-Activity
    Root, past subs; refuse if there is none; =rootOpen= it, start a session in that window, send
    =/bx-session-start emacs= register==.
  - =activityReach= (replaces =confirmHere=), =sessionReport=, =activityReport=.
  - The associations map AI-Activity directories to sessions (many to one; one AI-Activity may be
    associated with two sessions, rule 5).
- *The driver*: its Session row becomes
  session-start | session-report | activity-reach | activity-report | select-session.
  The newStart row's one-step start is =sessionStart=.
** -B|
####+BEGIN: blee:bxPanel:foldingSection :outLevel 1 :title "Open Points" :anchor "Open" :extraInfo "to discuss"
* [[elisp:(show-all)][(>]]  _[[elisp:(blee:menu-sel:outline:popupMenu)][±]]_  _[[elisp:(blee:menu-sel:navigation:popupMenu)][Ξ]]_       [[elisp:(outline-show-subtree+toggle)][| *Open Points:* |]] <<Open>>   to discuss  [[elisp:(org-shifttab)][<)]] E|
####+END
** +
1. Other sessions on the same AI-Activity (rule 5): Blee knows its associations; Claude alone can
   only see running sessions' directories (=~/.claude/sessions/=), which is engine-specific. How
   much of it belongs in =/bx-activity-report= (layer 0) and how much in Blee?
2. What =/bx-session-start= does in a session that is not new (already started, or after =/clear=).
3. Terminal Claude (claude-code.el): the same rules; its Session-Root is the directory it was
   started in. Nothing to build now, but the terms must fit it.
4. A nested AI-Activity Root (=initiate= run in a directory inside another root's tree) is its own
   home, so it is foreign to a session at the outer root although it lies under it. "Under the
   Session-Root" in the table is then only a first test; the home decides. Allow nested roots, or
   refuse =initiate= inside another root?
5. The order of work: layer 0 first (definitions in =AI-WORKFLOW.org=, the five commands), then the
   engine's documentation and figures, then blee/vscode-claude, then the panels.
** -B|
